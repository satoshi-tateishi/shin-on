# 機材管理システム 要件定義書

## 📋 システム概要

### プロジェクト名
**shin-on 機材管理システム**

### 目的
演劇・ミュージカル公演における機材の入出庫管理及び機材スケジュール管理を効率化するWebアプリケーション

### 技術基盤
- **フレームワーク**: Laravel 12 (PHP 8.4)
- **データベース**: MySQL 8.0
- **開発環境**: Docker (Laravel Sail)
- **認証**: LINE WORKS SSO
- **バックアップ**: Dropbox OAuth 2.0

### 技術的制約
- **MySQL 8.0制約**: EXCLUDE制約未対応のため期間重複チェックはアプリケーション制御中心
- **期間管理**: 複雑な日付範囲重複検証をLaravel側で実装
- **同時実行制御**: トランザクション + 楽観ロックによる整合性確保

---

## 🎭 業務要件

### 公演管理
- **年間公演数**: 約100公演（継続的に増加）
- **対象**: 演劇・ミュージカル公演
- **成長性**: レコード数の継続的な増加に対応

### 制作フェーズ管理
公演は複数のフェーズで構成される：

#### フェーズ例
- **パターン1**: 稽古場1 → 本番 → 旅公演
- **パターン2**: 稽古場1 → 録音 → 記者会見 → 稽古場2 → 本番

#### フェーズ特性
- 各フェーズには**使用期間**を設定
- **期間重複の回避**: 使用期間が重複しない機材のみ使用可能
- **柔軟なフェーズ構成**: 公演毎に異なるフェーズ構成に対応

## 🎛️ 機材管理要件

### 機材分類体系

#### 管理方式
1. **個体管理機材**: 機材個別に管理（シリアル管理）
2. **数量管理機材**: 在庫数量で管理

#### カテゴリ階層
```
大分類（例：ミキシングコンソール、スピーカー）
└── 中分類（例：デジタルミキサー、アナログミキサー）
    └── 機材アイテム
```

### 機材識別・管理

#### 個体管理機材
- **社内管理テキスト(通称:新音番号)**: "32ch-1", "5" など
- **同一名称機材**: 新音番号で個別識別
- **個別追跡**: 各機材の使用状況を個別管理

#### 数量管理機材
- **在庫算出**: 総数 - 使用数合計 = 在庫数
- **数量ベース管理**: 個別識別なし

### 機材規模
- **総アイテム数**: 約5,000個
- **変動性**: アイテム数の変動は少ない

## 🔧 機材セット管理

### セット概念
- **組み合わせ使用**: 複数機材を組み合わせて使用
- **個別使用**: セット構成機材の個別使用も可能
- **フレキシブル設計**: 機材故障時等のセット変更に対応

### セット操作
- **一括チェック**: 使用時にセット全体を一括チェック
- **一括返却**: 返却時にセット全体を一括処理

## 🏢 倉庫・保管管理

## 🛠️ データベース設計方針

### 機材管理テーブル設計
- **統合テーブル**: equipment テーブルで個体管理・数量管理を統一管理
- **管理区分**: `management_type` フィールドで個体/数量を区別
- **新音番号**: 個体管理機材の識別子として `shin_on_number` フィールド

### 期間重複チェック実装
#### 多重防御アプローチ
1. **UI段階**: リアルタイムでの使用可能機材表示
2. **Laravel段階**: FormRequestでの厳密なバリデーション
3. **DB段階**: トリガーによる最終防御

#### 重複チェックロジック
```sql
-- 期間重複判定
SELECT COUNT(*) FROM phase_equipment pe
JOIN phases p1 ON pe.phase_id = p1.id
JOIN phases p2 ON p2.id = ?
WHERE pe.equipment_id = ?
AND p1.start_date < p2.end_date
AND p1.end_date > p2.start_date
```

### 在庫管理設計
- **イベントソーシング**: 機材移動・使用の全履歴を記録
- **スナップショット**: 基準日時点在庫の高速計算
- **履歴テーブル**: `equipment_movements` で全移動を追跡

### セット管理設計
- **動的構成**: `equipment_set_items` による柔軟なセット構成
- **バージョニング**: セット構成変更時の履歴保持
- **個別使用**: セット構成機材の独立した使用可能性

## ⚠️ 既知の課題と対応方針

### 1. 期間重複チェックの複雑性
#### 課題
- MySQL 8.0ではEXCLUDE制約が使用不可
- 複雑な日付範囲の重複判定が必要

#### 対応方針
- Laravel FormRequestでの詳細バリデーション
- DBトリガーによる二重チェック
- UI側での事前警告表示

### 2. 機材セットの動的変更
#### 課題
- 故障時等の柔軟なセット構成変更
- セット使用中の個別機材取り出し

#### 対応方針
- セット構成のバージョン管理
- 個別機材の使用状況独立管理
- 段階的な制約緩和機能

### 3. パフォーマンス要件
#### 課題
- 5,000機材 × 100公演の大量データ処理
- 同時30ユーザーでの快適な操作

#### 対応方針
- 適切なインデックス設計
- クエリ最適化とN+1問題対策
- Redis等のキャッシュ活用

### 4. 在庫管理の時系列性
#### 課題
- 任意時点での在庫状況確認
- 履歴データの効率的な管理

#### 対応方針
- イベントソーシング + スナップショット併用
- 定期的な集計テーブル更新
- アーカイブ戦略による性能維持
